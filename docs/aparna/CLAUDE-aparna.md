# Project memory — Aparna's English Coaching CRM

Facts only. Procedures live in skills (`/aparna-loop`). Keep under 80 lines. EDITABLE: when Claude gets something wrong twice, or a human corrects it, add one line under Gotchas or Mistakes Log in the same session (encode-the-fix).

## What this is

- A fork of Atomic CRM, customised for an online English coaching business with global parents (WhatsApp-first).
- Planning pack: `docs/aparna/` — start with `README.md`. Authority: `decisions.md` (accepted) > `MVP.md` (during the MVP track) > `PRD.md` / `ARCHITECTURE.md` / `project_plan.md` / `features.json` > upstream conventions > anything else.
- **Current track: MVP** (`MVP.md`, slices M0–M5). Full-build slices S1–S10 start only after the MVP exit gate, through `TRANSITION.md`.

## Domain names (code ↔ UI)

- `contacts` = Parent. `deals` = Admission. `sales` = Staff user.
- Admission stages: `enquiry`, `trial_booked`, `trial_done`, `payment_pending`, `enrolled`, `lost`.
- MVP: child and fee fields live on `deals` (ADR-A12). Full build adds `students`, `courses`, `batches`, `trials`, `enrolments`, `invoices`, `attendance`, `progress_notes`, `messages`.

## Commands

- Cloud session start: `npm ci` (on `ENOTEMPTY`: `rm -rf node_modules`, repeat); then `npx playwright install chromium` (after `npm ci`: the repo pins a newer browser build); if `docker info` fails: `sudo sh -c 'nohup dockerd > /tmp/dockerd.log 2>&1 &'` (the `service` wrapper is hook-blocked); then `make start`.
- Verify: `make typecheck`, `make lint`, `make test`, `npm run test:unit:functions`, `npx supabase test db` (pgTAP), Playwright e2e. CI `Check` re-runs them on the PR.
- Schema: edit `supabase/schemas/*.sql`, then `npx supabase db diff --local -f <name>`; never hand-write migrations unless ADR-A15 falls back.

## Rules that are easy to miss

- Only `passes` may change in `docs/aparna/features.json`. MVP slices from M1 (light mode, ADR-A20): it flips when the slice PR's `Check` is green; `manual:` features only on the human's confirmation.
- MVP slices M1–M5 run in light mode (ADR-A20); steps in /aparna-loop.
- MVP: **no Teacher accounts** until F-101 passes (ADR-A14). Only Owner and Counsellor; a `sales` trigger caps active staff at 2 (M-108); SSO stays off.
- MVP: the next-action DB check is a closed list (`stage not in ('enrolled','lost')`), so stages are read-only in Settings (a saved DB config overrides defaults per key, P-15).
- Real student or enquiry files never enter a cloud session or git; importers are tested with synthetic CSVs only.
- MVP WhatsApp = `wa.me` links from `src/components/atomic-crm/whatsapp/templates.ts`. No WhatsApp API calls in the MVP.
- Every new field or resource needs FakeRest generator updates (Vercel Preview and harness smoke run in demo mode).
- Times: store UTC; display with `formatInZone()`; parents have an IANA `timezone`; batch and staff times are IST.
- Money in paise (`bigint`), never floats.
- Our changelog is `docs/aparna/CHANGELOG.md`. Never edit root `CHANGELOG.md` (regenerated by script).
- Staff are referred to by role (Owner, Counsellor, Teacher) in code, docs and commits — never by personal name.
- The Owner is "the Owner" / "the Owner's account" in every committed file; the only allowed use of the name is the trade name "Aparna's English Coaching".
- One branch + one PR per slice; PR title starts with the slice id, e.g. `[M2]`. Never push to `main`; the human merges.
- Parallel slices touch only the files they own (`MVP.md` §7). Need another slice's file → stop and ask.

## Gotchas

- `deals.lost_reason` was dropped upstream; we re-add it on purpose (ADR-A03).
- Upstream RLS is `using (true)`; any table we touch in the full build gets role policies (ADR-A07).
- `demo/App.tsx` does not use `src/App.tsx`; domain options go in `root/defaultConfiguration.ts` (P-11).
- Planning chat sandboxes are not Claude Code cloud sessions: check facts about the cloud VM in code.claude.com docs or in the session itself (P-10).
- First user on a fresh Supabase project becomes the administrator (R-13): sign-ups are OFF in Supabase Auth from project creation; first account from the dashboard after the first Deploy, all others by invitation (ADR-A19).
- Until handover (M-504): Supabase and Vercel in the developer's account, test accounts on developer email aliases, synthetic data only (ADR-A20).
- CI keeps sign-ups on only in `supabase/config.e2e.toml` (the onboarding spec signs up through the UI); production Supabase Auth stays off (R-13).
- `mark_fee_paid` advances by calendar month: 31 Jan → 28 Feb, then the due day stays on the 28th (accepted by the Owner, M1).
- The app merges parents through the `merge_contacts` edge function, which calls SQL `public.merge_contacts`; demo mode merges in `providers/commons/mergeContacts.ts`. Keep both rule sets equal.
- Cloud session proxy: Docker containers do not trust its CA, so `supabase db diff` (migra) and local edge functions fail to fetch packages. Generate migrations with `--use-pg-delta --db-url` against a throwaway instance built from `supabase/schemas`; serve edge functions with an `--env-file` that sets `SSL_CERT_FILE` / `DENO_CERT` / `DENO_TLS_CA_STORE` to a CA copy under `supabase/functions/` (P-26).
- Supabase client calls return `{ error }` and do not throw; every security-relevant write must check it (P-30).
- `bash-guard` refuses Playwright e2e for every caller, the main session included: e2e specs are verified by the CI `e2e-test` job (P-27).
